Guide

Everything you need to integrate a Turkish TRY ⇄ USDC ramp against this sandbox — and to understand what a production anchor in Türkiye actually does behind the same API shape.

Overview

TR Mock Anchor is a sandbox anchor: a service that moves value between Turkish lira in the banking system and USDC on Stellar. It is API-key based (no SEP-10/SEP-24 interactive flows) because that is how Turkish exchanges and payment institutions expose ramps to partners: your backend holds a key and drives the customer journey from your own UI.

The model mirrors a Turkish exchange:

  1. Your user is registered as a customer (KYC: name, T.C. Kimlik No, IBAN).
  2. The customer sends TRY by bank transfer to the anchor's IBAN and writes a personal reference code in the description.
  3. The anchor matches the transfer → the customer has a TRY balance.
  4. The customer buys USDC at the USD/TRY rate and it is paid on Stellar to their wallet.
  5. Off-ramp is the reverse: send USDC with a memo → TRY balance → payout to the IBAN.
Try it live: How it works runs the full round trip from your browser with real testnet transactions. The API reference documents every field.

Concepts

Accounts & API keys

An account is you, the integrator. Sign up with an email and password on the home page (or POST /v1/partners). Each account has exactly one API key (trma_test_…), visible in the dashboard and rotatable at any time. Send it on every request:

X-API-Key: trma_test_…          # or
Authorization: Bearer trma_test_…

Everything you create — customers, orders, webhooks — is scoped to your account. Other accounts cannot see it.

Keys are sandbox credentials and are stored in clear so the dashboard can show them again. Treat this deployment as public testnet infrastructure: never reuse these passwords or keys elsewhere.

Customers & KYC

A customer is one of your end users. Create one with POST /v1/customers:

{
  "external_id": "user_42",              // your own id, unique per account (optional)
  "first_name": "Ayşe", "last_name": "Yılmaz",
  "tckn": "10000000146",                  // T.C. Kimlik No, checksum-validated (optional)
  "iban": "TR330006100519786457841326",   // Turkish IBAN for payouts (optional, mod-97 validated)
  "email": "ayse@example.com"
}

The response carries kyc_status and a unique deposit_reference such as TRMA-7K2M-Q9XZ. KYC is instant in the sandbox: approved unless first_name is REJECT or PENDING, which produce the other states so you can build the UI for them. POST /v1/sandbox/customers/{id}/kyc flips the state later. Only approved customers can ramp.

Turkish rails: IBAN, FAST/EFT/Havale, açıklama

Retail money in Türkiye moves between bank accounts identified by a 26-character IBAN (TR + 2 check digits + 5-digit bank code + 1 reserved digit + 16-digit account). Transfers run on three rails: FAST (instant, 24/7, the default for retail amounts), EFT (interbank, business hours) and Havale (same bank). Every transfer carries a free-text description — the açıklama.

Exchanges credit deposits by matching that description: each customer gets a personal reference code and is told to write it in the açıklama when sending money to the exchange's IBAN. Transfers without a recognisable reference are held and matched manually by support. This sandbox reproduces both paths:

  • GET /v1/customers/{id}/deposit-instructions returns the bank name, IBAN, account holder, the customer's reference and bilingual instructions — show this in your app.
  • POST /v1/sandbox/bank-transfers {"reference","amount_try"} is the bank telling the anchor "a transfer with this description arrived". A matching reference credits the balance (HTTP 201). An unknown one is held as unmatched (HTTP 202) until you …/assign it to a customer — the support-desk path.

Balances & ledger

Each customer has a TRY balance (2 decimals) and a USDC balance (7 decimals, Stellar's precision). All amounts in the API are decimal strings; the service does fixed-point integer math internally and never rounds up in the customer's favour. Every movement is an append-only ledger entry (GET /v1/customers/{id}/ledger) with a kind:

kindcurrencywhen
bank_transferTRY +a TRY transfer was matched to the customer
onrampTRY −on-ramp created (debited up front)
onramp_refundTRY +on-ramp failed permanently
offramp_depositUSDC +USDC arrived for an off-ramp
offramp_convertUSDC − / TRY +the deposit was sold for TRY
payoutTRY −TRY sent to the IBAN

Rates, quotes & spread

The anchor treats USDC as 1 USD and prices USDC/TRY off the USD/TRY mid rate read from Reflector's foreign-exchange oracle on Stellar mainnet (contract CBKGPWGK…MCJZC, via simulateTransaction, cached 60 s). If the oracle is unreachable it falls back to a static rate and reports rate_source: "static_fallback".

A flat spread (default 50 bps) is applied on each side: buy_rate = mid × (1 + spread) when the customer buys USDC, sell_rate = mid × (1 − spread) when they sell. There are no fixed fees. GET /v1/rates shows all three numbers.

A quote (POST /v1/quotes) locks a rate for 120 seconds and is single-use. Fix either side of the conversion:

{"side":"buy",  "amount":"1000.00",  "amount_currency":"TRY"}   // spend 1000 TRY → how much USDC?
{"side":"buy",  "amount":"25",       "amount_currency":"USDC"}  // want 25 USDC → how much TRY? (rounded up)
{"side":"sell", "amount":"25",       "amount_currency":"USDC"}  // sell 25 USDC → how much TRY?

Quotes are optional: on-ramps accept amount_try and off-ramps amount_usdc at the live rate instead of a quote_id.

Flows

On-ramp (TRY → USDC)

sequenceDiagram
  autonumber
  participant U as Customer
  participant App as Your app
  participant A as TR Mock Anchor
  participant B as Bank (simulated)
  participant S as Stellar testnet
  App->>A: POST /v1/customers
  A-->>App: customer + deposit_reference
  App->>U: show IBAN + reference
  U->>B: TRY transfer, açıklama = reference
  B->>A: POST /v1/sandbox/bank-transfers (you, in the sandbox)
  A-->>App: bank_transfer.received · TRY balance credited
  App->>A: POST /v1/quotes (buy)
  App->>A: POST /v1/onramps {quote_id, destination_address}
  A-->>App: status pending (TRY debited)
  A->>S: payment or createClaimableBalance (USDC)
  A-->>App: onramp.completed + stellar_tx_hash

POST /v1/onramps needs customer_id, destination_address (a G… or muxed M… address) and either quote_id or amount_try; memo (≤28 chars text) is optional. The TRY is debited immediately and the order is pending. A worker settles pending orders every few seconds and the order becomes completed with settlement, stellar_tx_hash and, for claimable balances, claimable_balance_id. If the send fails permanently the order is failed and the TRY is refunded.

Limits: 50.00 – 250,000.00 TRY per order (configurable).

Off-ramp (USDC → TRY)

sequenceDiagram
  autonumber
  participant U as Customer wallet
  participant App as Your app
  participant A as TR Mock Anchor
  participant S as Stellar testnet
  App->>A: POST /v1/offramps {customer_id, amount_usdc?}
  A-->>App: deposit.address + deposit.memo (id), rate locked 30 min
  App->>U: show address + memo (or a muxed address)
  U->>S: payment USDC → treasury, memo id
  S-->>A: watcher sees the payment
  A-->>App: offramp.deposit_received (USDC balance +, sold for TRY)
  A-->>App: payout.completed (TRY → IBAN, simulated)
  A-->>App: offramp.completed

POST /v1/offramps returns a deposit object: the treasury address, memo_type: "id" and a 12-digit memo. The customer's wallet must send USDC to that address with that memo (or to a muxed address whose id equals the memo). amount_usdc is informational — the anchor converts whatever amount actually arrives. The rate is locked for 30 minutes; later deposits are repriced at the current sell rate and flagged repriced: true.

By default auto_payout is true: the TRY is paid to payout_iban (or the customer's IBAN) as soon as the deposit lands, and payout_id points at the payout. Set auto_payout: false to leave the TRY on the balance and pay out later with POST /v1/payouts. Off-ramps that have not received a deposit can be cancelled.

Payments without a usable memo, with an unknown memo, or to a cancelled/completed off-ramp cannot be attributed. They are parked under GET /v1/sandbox/unmatched-deposits. In production a support process would return or assign them — make your UI show the memo prominently.

Payouts

POST /v1/payouts {"customer_id","amount_try","iban"?} debits the TRY balance and records an instant FAST-style transfer with a bank_reference. In production this is where settlement times (FAST is near-instant; EFT follows banking hours) and payout limits would appear.

Settlement details

  • Payment vs claimable balance. If the destination account exists and trusts the sandbox's USDC, the anchor sends a regular payment. Otherwise (account unfunded, or no trustline) it creates a claimable balance with the destination as the sole, unconditional claimant. The wallet claims it after adding the trustline — see wallet-side notes. This is the same approach production ramps such as Etherfuse use for first-time wallets.
  • Muxed destinations. An M… address is paid as such when the base account has a trustline; claimable balances always go to the base G… account.
  • Memo on on-ramps. Optional text memo, truncated to 28 bytes.
  • Treasury. One account pays every on-ramp and receives every off-ramp: see GET /health. If it runs low, on-ramps wait with pending_reason: "treasury_low" and settle once it is refilled — they do not fail.
  • Idempotency. Quotes are single-use; each off-ramp has a unique memo; a deposit transaction is processed at most once.

Webhooks

Register with POST /v1/webhooks {"url":"https://…","events":["*"]}. The response includes a secret (shown once). Each event is POSTed as JSON:

POST https://your-app/hook
Content-Type: application/json
X-TRMA-Event: onramp.completed
X-TRMA-Delivery: whd_…
X-TRMA-Signature: t=1724590000,v1=3f2a…   # hex HMAC-SHA256(secret, "<t>.<raw body>")

{"id":"evt_…","type":"onramp.completed","created_at":"…","data":{ …the on-ramp object… }}

Respond with any 2xx within 8 seconds. Failures retry after 5 s, 30 s, 2 min and 10 min, then the delivery is marked failed (GET /v1/webhooks/{id}/deliveries). Verify signatures against the raw body:

// Node
import { createHmac, timingSafeEqual } from 'node:crypto';
export function verify(rawBody, header, secret) {
  const { t, v1 } = Object.fromEntries(header.split(',').map((p) => p.split('=')));
  const expected = createHmac('sha256', secret).update(`${t}.${rawBody}`).digest('hex');
  return v1.length === expected.length && timingSafeEqual(Buffer.from(v1), Buffer.from(expected))
    && Math.abs(Date.now() / 1000 - Number(t)) < 300;
}
# Python
import hmac, hashlib, time
def verify(raw_body: bytes, header: str, secret: str) -> bool:
    parts = dict(p.split('=', 1) for p in header.split(','))
    expected = hmac.new(secret.encode(), f"{parts['t']}.".encode() + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(parts['v1'], expected) and abs(time.time() - int(parts['t'])) < 300

Event types: customer.created, customer.kyc_updated, bank_transfer.received, bank_transfer.unmatched, onramp.created, onramp.completed, onramp.failed, offramp.created, offramp.deposit_received, offramp.completed, payout.completed.

Event log (polling)

No public endpoint? Poll GET /v1/events?after=<last event id>&limit=200. Events are returned oldest-first; keep next_after as your cursor. Filter with type=. The same payloads are delivered here and by webhook.

Wallet-side notes

  • Trustline first. To receive USDC as a plain payment the wallet needs a trustline to USDC:<issuer from /health>. Freighter (testnet) and Stellar Lab can add one.
  • Claiming. If settlement is claimable_balance, the wallet adds the trustline and submits claimClaimableBalance({ balanceId }) (Freighter shows claimable balances in its UI). Both can go in one transaction — see the demo.
  • Memos on off-ramps. Always memo_type: id. Wallets that cannot set a memo can pay a muxed M… address built from the treasury and the memo id (new MuxedAccount(treasury, memo).accountId()).
  • Exact amounts. The off-ramp converts what arrives, so partial or oversized payments still complete; only the memo must be right.

From sandbox to a real anchor

The API shape is deliberately close to what a Turkish anchor would expose to partners, so the parts of your integration that change are predictable:

  • Bank transfers become real. POST /v1/sandbox/bank-transfers disappears; the anchor's bank integration credits balances, typically within seconds on FAST. Expect delays and the unmatched-transfer path to matter.
  • KYC becomes real. Customer creation returns pending until identity checks pass; you will handle document upload or a hosted KYC page and customer.kyc_updated events. Limits depend on KYC tier.
  • Payouts have schedules and limits. FAST caps per transaction; EFT runs in banking hours.
  • Pricing is a live book. Spreads move with liquidity; quotes are shorter-lived.
  • Mainnet asset. USDC's mainnet issuer is GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN; trustlines and treasury addresses change.
  • Credentials. Production keys are scoped, rotated and never stored in clear; some anchors add request signing (HMAC of body + timestamp) on top of the key.

FAQ

Why not SEP-24 / SEP-6?
Those standards target wallet-initiated flows with the anchor's own UI. Turkish exchanges expose partner APIs where the integrator owns the UI and holds a key; this sandbox mirrors that reality so hackathon code transfers.
Can I use this from a browser app?
CORS is open for the sandbox, but the API key is a server credential. Keep it in a backend; use the browser only for the wallet side (signing the off-ramp payment, claiming balances).
My on-ramp is stuck in pending.
Check pending_reason. treasury_low means the shared treasury needs USDC; retrying: … means Horizon hiccups. Both resolve on their own.
My off-ramp never completes.
The payment probably lacked the memo, used memo_type: text, or went to the wrong address. Look in GET /v1/sandbox/unmatched-deposits.
Why did I get 99.00 TRY back from 100 TRY?
Two crossings of a 50 bps spread ≈ 1%. That is the anchor's revenue model.
Is the data persistent?
Yes, but this is a shared sandbox: assume it can be reset before events.
